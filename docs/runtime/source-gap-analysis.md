# Orchestration inventory and runtime reconciliation

> Historical integration-design baseline, 2026-11-02. See [current public distribution](../current-release.md) for shipped components and adopted publication decisions. Proposed runtime behavior remains unimplemented.

This is a design and migration plan. No runtime, connector, scheduler, specialist inference, website change or publication is implemented by this document. The proposed public project combines one method entry with fourteen logical roles and a portable execution contract. A role profile is instructions for a bounded invocation; it is not an autonomous worker, persistent model process, authenticated connector or delegated authority.

## Evidence and source boundary

The extracted agent pack contains **33 regular files**: 30 under `package/`, two top-level historical delivery/verification records and one observer test file. `orchestrator-source-map.csv` maps each actual file once. The original archive and extracted sources remain private and unchanged. Public destinations in that table are proposed paths, not files already migrated.

Direct inspection establishes the fourteen role profiles, configuration, observer source and ten helper tests. All **29** file hashes listed in `package/agents/package-manifest.v1.json` match the extracted bytes. The thirtieth package file is the manifest itself, which is not self-listed. This verifies internal consistency of these received bytes, not their authenticity, current installation, policy approval or clinical/production suitability.

The ten observer unit tests were rerun with `python -m unittest discover -s analysis_inputs/agents_pack/tests -v`: all ten passed. They exercise local helper behavior using temporary synthetic files. They do not invoke `observe()`, import the native coordinator, inspect a website, install a schedule or call a model. Test-generated bytecode caches were removed. Neither `observe.py validate` nor `observe.py observe` was executed; the former also depends on missing deployment evidence.

`FINAL_VERIFICATION.json` and the installation report are dated historical assertions. They report a Windows task, a Global response, 45 preserved core source hashes, 46 compiled hashes, a historical 48-test core suite and a local validation count of 74. The corresponding core source, compiled artifacts, core suite, native coordinator store, policy files, schedule action and real operation receipts are not present in this archive. Preserve these as **reported historical evidence**, never as freshly reproduced results. The count of 74 is consistent with the manifest's 29 listed package files plus the reported 45 core source files, but the missing proof manifest prevents direct confirmation.

## Source deployment defaults and public routing

These are **exact historical configuration values**, not claims that a model is currently available from a provider or host. All fourteen role entries and profiles bind to `gpt-6.1-terra` with `reasoning=medium`. `COMMON.md` and the report state `gpt-6.1-sol/high` for the external Global coordinator. `validate_config()` rejects any role route other than the exact Terra/medium pair. The public catalog instead uses provider-neutral routing aliases `analysis` and `review`; provider/model/version/reasoning belongs to a private deployment binding and actual executor attestation.

The historical deployment limits are: one parallel specialist; one delegation level; two refinement passes; two safe-read retries; one escalation; 30 task minutes; eight model calls per task; zero incremental paid budget in EUR; zero idle inference. The daily call cap is the string `inherited-cumulative-from-.coordinator/model-policy.json`, not a number. The governing policy file is absent. Do not interpret the string as unlimited allowance or reset cumulative usage. The source plan's ceiling of three parallel specialist tasks is superseded by the deployment's tighter limit of one. The skill's tentative two public requests in parallel is a separate request-concurrency hypothesis, not the specialist limit or a supplier quota.

Keep these distinctions in the migration ledger. Public defaults should support a useful offline/read-only path without a model provider, and allow an actual host to supply stricter limits. An alias must resolve before invocation; an unresolved model, unavailable tool or missing budget is a blocked dependent capability, while independent deterministic inspection continues. No tool presented in an interactive host is presumed to exist in a persistent or unattended runner.

## Observer semantics: what it actually does

`inspect(root)` assumes a root containing the hardcoded tenant-specific child directory. It reads config and the 29-entry package manifest there, then requires `evidence/core-verification.v1.json` and its `sourceManifest`. The proof file is absent from the delivered pack. It also reads four policy paths relative to the outer root. Therefore the archive is not a standalone runnable deployment, and `validate` cannot be advertised as an out-of-box success command. The command's default root is derived from `__file__.parents[2]`, which only has the intended meaning in the original installed layout.

`safe_file()` rejects absolute paths, Windows drive paths, `..` components, symlinks and supported junctions, then checks resolution stays under the selected root. `check_files()` limits each manifest call to 200 entries, treats a missing file as `unavailable`, a file larger than 4,000,000 bytes as `unreadable_size_limit`, and otherwise records the actual SHA-256 with `verified` or `changed`. It never reports a missing source as healthy or zero. `observation_key()` sorts file rows by path and fingerprints file states/digests plus policy digests. A path-order change alone is not novelty.

`validate_config()` checks exactly O0 plus S1–S13, matching count 14, exact historical model pair, instruction file existence, four execution flags fixed false, parallel specialists fixed one and refinement passes fixed two. It does **not** implement the complete project/work-order/connector/authority/budget contract. The `validate` CLI returns 2 for reported validation errors or file mismatches; uncaught missing/invalid deployment files can fail before a structured result is printed. A passing helper test is not evidence this CLI is runnable from the received archive.

`observe()` is **stateful** even when `notify=False`: it imports the external native store, acquires a 120-second lease, reads private state and writes `latest-report.json` and `checkpoint.json`. With `--notify-native`, it may additionally call `Store.submit()` with a status task and stable notification key. It is free of model/site calls by its own implementation, but the external coordinator may analyze a newly submitted request with separately accounted inference. “No product writes” must not be described as “no side effects.”

Delivery intent is persisted before submission. A pending uncertain intent is reused exactly, including its generation, fingerprint, message and key. An observation without notification does not acknowledge delivery. A return to an older evidence fingerprint after a different delivered state gets a new generation. Repeated already-notified evidence is suppressed. If pending state A is submitted while current evidence is B, A is preserved for reconciliation and a subsequent invocation can deliver B; document this delayed catch-up behavior rather than assuming the latest observation is always the submitted notice.

The local checkpoint is explicitly deduplication state, not a task authority. Lease acquisition failure defers the observation. The lease is released and store closed in a `finally` after inspection; the supplied code has no lease renewal or fencing check during filesystem work. The portable design must define the adapter's expiry and delivery semantics rather than infer them from names of native methods.

## Contract gaps that migration must resolve

1. **Configuration versus project/work-order contract.** The deployment JSON has a project ID and role defaults but lacks explicit tenant/site/environment, allowed public hosts, current mandate validity, run identity, exact operation allowlists, evidence coverage, per-run tool/page/byte limits and domain authority attestations required by the operational and skill contracts. Add versioned contracts and validate at actual operation boundaries. Do not expand the legacy role validator and claim it enforces everything.
2. **Finding envelope versus shared records.** `finding.schema.json` is an additive narrow envelope with nine required fields (`id`, `site`, `resource`, `kind`, `evidence`, `owner`, `nextAction`, `state`, `uncertainty`). It has no version/source revision, timestamps, locale/layer, reproduction, severity/consequence or coverage fields. The skill requires stable/versioned provenance records and separate states for editorial acceptance, price, availability, deployment, index and outcome. Define a common envelope or versioned linked records without forcing every optional field onto a trivial finding. Preserve compatibility explicitly; the source itself says it does not replace the unavailable core contracts.
3. **Connector counts versus operational capability.** Reconcile C01–C25, the ten JSON summary IDs and CON-01–CON-28 by operation and field effect, not by row count. A Wix API operation, HTTP capture, indexed-state report, AI UI export and consumer model trial have different semantics. Preserve `unsupported`, `partial`, `unavailable` and `unqualified`; availability is not authentication, read access is not write access and current chat access is not recurring credentials.
4. **Policy discovery versus enforceable policy.** Missing policy files produce `None` digests and no dedicated validation error in the current inspector. If manifests otherwise match, this can look like passing readiness with missing authority inputs. Proposed inspection should report each required/optional dependency explicitly and with a fail-closed result only for actions dependent on it; offline evidence analysis must remain usable.
5. **Input bounds versus total work bound.** Manifest entry count and per-file data size are bounded, but JSON config/manifest/proof reads and policy digest reads occur outside those checks. There is no aggregate byte, elapsed-time or lease-heartbeat budget in `inspect()`. Add schema/size limits before parse and a total deadline. These are robustness gaps and optional hardening until an actual lower-trust input principal and reachable consequence are demonstrated; do not label them proven exploitability.
6. **Hash consistency versus trust.** A manifest stored alongside mutable source is not an authenticity anchor. Define trusted release/source provenance and immutable candidate identity without requiring an unnecessary universal signing service. Any future mutation checks target/base revision and authority independently of model output.
7. **Filesystem boundary versus race semantics.** Tests cover obvious path traversal and one symlink case. They do not establish race-free traversal, Windows junction coverage on this host, special-file behavior or protection from a lower-trust process changing paths after validation. Specify supported threat model/filesystem and use appropriate bounded file-opening behavior if that principal is in scope; classify unproven race concerns as hypotheses.
8. **Reported limits versus enforcement.** Most config limits are only values; the observer checks two. No provided executor enforces eight calls, 30 minutes, budget accounting, one escalation, revocation, independent-review ordering or zero idle inference. Implement and test these in a later engine/adapter phase, with budget reserved for verification/recovery.
9. **Missing coordinator contract.** `Store.lease`, `submit`, `release`, `close` are used but their implementation, errors, atomicity, idempotency, lease-token guarantees and revocation behavior are not supplied. A new adapter must match real authority semantics; a local fake cannot certify the private native service.
10. **Scheduling versus recurring qualification.** A Windows receipt does not prove cross-platform runner availability, token renewal, unattended tools or public crawl schedules. The source task requires an interactive user and host. Define supported operation modes: manual offline, host-assisted, and explicitly qualified unattended deployment. Do not silently install a daemon or import an interactive browser session.

## Proposed portable runtime boundary

`skills/seo-geo/SKILL.md` is a thin methodology entry; `agents/COMMON.md` and `agents/profiles/` define logical roles. `catalog/agents.csv` is the public form of `catalog/agents.csv`. `catalog/connector-operations.csv` describes operations and evidence requirements, while an actual deployment keeps accounts, identities, credentials, principals and model IDs private. Versioned schemas live in `contracts/`, their semantics in `docs/contracts/`, runtime designs in `docs/runtime/`, and concrete host boundaries in `adapters/`.

Proposed Rust crates, **design only**:

| Proposed crate | Responsibility | Explicit external boundary |
|---|---|---|
| `crates/seo-geo-contracts` | Versioned project/work-order/observation/finding/proposal/receipt/evaluation types and validation | Compatibility with received skill/helper records and any later recovered core contracts |
| `crates/seo-geo-policy` | Evaluate supplied authority, data/destination, action/field and budget preconditions | Cannot grant authority, discover credentials or become a second permissions service |
| `crates/seo-geo-state` | Evidence, checkpoints, operation intents, receipts and durable recovery views | External coordinator/tracker stays task authority; storage technology selected only after requirements |
| `crates/seo-geo-engine` | Bounded workflow, deterministic checks, invocation dispatch, review ordering and recovery state machine | Host-provided model/tool adapters; no assumed interactive plugin or persistent model process |
| `crates/seo-geo-cli` | Explicit offline validation/inspection, candidate generation and host-assisted commands | Separate pure inspection from stateful notify/execute; side effects visible in command and receipt |

Adapters for coordination, scheduler, model and provider operations translate the typed contract into capabilities that are actually present. They declare identity, exact target, scopes, limits, version, idempotency/revision semantics, side effects, qualification expiry and receipts. A publishing adapter is narrow technical execution by the native writer, not an additional unconstrained agent. Rust is an implementation-language proposal, not a new authority or proof of safety.

The legacy TypeScript core must first be recovered and assessed at an exact revision. Obtain its license, package/lockfile, API/schema exports, fixtures and the historical 48-test definition. Build a contract crosswalk and keep unsupported behavior explicitly unavailable. Prefer wrapping a reusable stable core or using common fixtures before deciding to port. A Rust implementation must demonstrate semantic parity on shared sanitized fixtures, especially null/zero/unknown, HTML/header observation layers, draft/live/verified states and operation recovery. No Rust code or successful migration is claimed in this plan. No frontend conversion follows merely from a backend language choice.

`tools/readiness-observer/observe.py` remains a proposed retained component through portable interfaces. It should support pure inspection with injected roots/manifests/policy dependencies, then a separate opt-in coordination/state adapter for notification. It must never initialize a replacement native authority on first use. Any future equivalent Rust implementation should pass the same behavioral fixtures before replacing it; retain the simpler Python tool if migration cost has no demonstrated benefit.

## Migration acceptance and verification plan

**Phase 0 — evidence and publication candidate.** Every one of the 33 supplied files has a source hash and proposed disposition. Preserve O0 and S1–S13. Keep raw tenant sources out of public history. Review the English candidate for personal paths, private Library IDs, internal UUIDs, owner IDs, credentials, clinical/transactional data and unsupported availability claims. Inventory licenses/attribution before copying source; unknown license is a tracked reuse decision, not silently granted permission. No repository publishing is performed by this plan.

**Phase 1 — pure method and contracts.** Validate schemas/examples; preserve multi-dimensional state and provenance; produce useful offline findings without coordinator, model provider or network. Reconcile source-plan versus deployment limits explicitly. A valid example is not a ready deployment. All catalog capabilities remain unqualified until real operation evidence exists.

**Phase 2 — observer portability.** Retain the ten existing regressions, then add tests for malformed/missing config/manifest/proof, required missing policy, invalid role IDs/models resolved by alias, entry/file/aggregate/time limits, absolute/drive/traversal/symlink/junction paths on supported systems, output create/replace behavior and explicit side-effect separation. Pure inspection must not import Store, acquire a lease, write outside its supplied output or notify. Test configuration may replace the exact historical provider pair with an alias; this is a versioned migration, not a claim the old validator already supports it.

**Phase 3 — fake-adapter fault tests.** Exercise lease busy/expiry/lost ownership; close/release failure; duplicate events; reordering; crash before saved intent, before submit, after accepted submit and before saved acknowledgement; A→B→A recurrence; pending A with current B; corrupt/truncated checkpoint; bounded retry; clock differences and notification generations. Confirm each intentional native notification has an auditable task reference and no parallel authoritative queue. Test with deterministic clock/state and fake coordinator only; passing does not certify the actual private service.

**Phase 4 — recovered core and Rust decision.** Recover exact TypeScript source and provenance, run its own meaningful suite in isolation and compare semantic fixtures. Document retained/wrapped/replaced capabilities and gaps. Only implement proposed Rust crates after the design is accepted. A later migration passes shared contracts/fixtures and recovery behavior at acceptable operating cost; source hash counts or language choice alone do not satisfy parity.

**Phase 5 — qualified host assistance.** With a real deployment mandate, demonstrate exact project/site/identity, source policy version, configured model alias resolution, actual tool registry, independent review ordering, cumulative budget accounting, revocation/STOP and current task/resource claim. A model call receipt proves that exact invocation only. Session tools remain host-provided and can disappear; missing operations preserve useful independent work and explicit unknowns.

**Phase 6 — optional recurring or write qualification.** Only after an actual recurring mandate, inspect existing schedules to avoid duplication and qualify scheduler identity/timezone/DST/restart/renewal/retention. Only after a field/action-specific write mandate, verify current base, native writer, allowed exact operation, intent/dedup, partial/unknown reconciliation, public propagation and drift-aware rollback. Stop tests before real bookings, payments, notifications or personal records. Success requires no critical privacy/intentional-policy/booking regression, sufficient independent quality, practical cost and a clear retain/reject/inconclusive decision. Production and domain acceptance remain separate records.

## Main risks and accountable next actions

The principal risk is overstating readiness: profile installation, a local observer and catalog entries can look like a working autonomous SEO system even though the archive supplies no qualified executor, real connector binding or candidate core. The next risk is publishing tenant/host assumptions as universal public defaults. A third is porting unavailable TypeScript behavior into Rust by guesswork, creating incompatible contracts and a duplicate coordinator. A fourth is treating a stateful observer as harmless read-only validation. The plan addresses these through explicit evidence labels, a complete source disposition map, external authority/coordination adapters, provider-neutral routes, operation-level qualification and fault-oriented migration acceptance.

The next concrete deliverables are the unified English contract/schema plan, connector-operation crosswalk, redacted public file candidate and recovered-core request list. Until those are available, keep legacy coordinator, schedules, website writers, runtime policies and source files unchanged.
